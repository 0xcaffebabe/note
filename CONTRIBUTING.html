贡献指南

欢迎补充知识内容、修正文档错误、修复缺陷或改进站点功能。解决 issue 的改动必须通过 Pull Request（PR）提交，并遵循项目现有的设计、架构与代码规范。

从 issue 到 PR

  1. 开始前搜索已有 issue 和 PR，了解问题背景、讨论结论与验收要求，避免重复工作。新问题请说明现象、预期行为和复现步骤；内容纠错请给出文档位置与依据。
  2. 处理已有 issue 时，在 issue 中说明计划与处理范围。涉及架构、交互或设计约定的较大调整，先讨论方案。
  3. 从最新的 `master` 创建工作分支；没有仓库写权限时，先 Fork 再创建分支。一个 PR 聚焦一个问题，避免夹带无关重构、格式化或依赖升级。
  4. 完成修改和必要验证后，向本仓库的 `master` 提交 PR。只提交本地修改或在 issue 中描述方案，不代表完成交付。
  5. 在 PR 描述中关联 issue：完整解决时使用 `Closes #123`，仅完成部分工作时使用 `Refs #123` 并说明剩余事项。
  6. 根据评审反馈完善同一个 PR，修复相关检查失败；通过评审及 CI 检查后由维护者合并。issue 是否解决以合并后的实际结果为准。

设计与代码规范

设计与交互

修改页面、组件或样式前，阅读并遵循 DESIGN.html。需要改变既有设计约定时，应说明原因并同步更新设计文档。

  • 复用现有组件、布局模式和语义设计令牌，不随意硬编码颜色、间距、层级或响应式断点。
  • 保持亮色、暗色和不同屏幕尺寸下的表现一致，优先使用 CSS 响应式布局。
  • 异步内容提供加载态、空态和错误态；保留键盘操作、可见焦点、语义标题与链接行为。
  • 图表复用统一主题与生命周期管理，避免重复实现初始化、主题切换和资源释放。

设计文档中的部分路径尚未随目录调整更新，当前实现入口为：

  • 设计令牌：[src/platform/web/style.less](src/platform/web/style.less)。
  • 响应式断点：[src/core/config/breakpoints.ts](src/core/config/breakpoints.ts) 与 [src/breakpoints.less](src/breakpoints.less)。调整断点时同步维护相关样式和测试。
  • 图表基建：[src/platform/web/util/echart/](src/platform/web/util/echart/)。

架构与代码

  • 遵循现有目录职责：`src/core/` 放置核心业务逻辑与端口接口，`src/adapters/` 实现平台或第三方能力适配，`src/platform/` 负责平台入口、组装和界面。核心逻辑通过端口使用外部能力，避免直接耦合浏览器或 Node.js API。
  • 沿用所在文件和相邻模块的命名、缩进、导入方式及 Vue 组件组织风格，避免为个人偏好进行整文件格式化。
  • 遵循 [tsconfig.json](tsconfig.json) 的类型约束，明确接口和数据边界，避免无理由使用 `any` 或忽略类型错误。
  • 优先复用已有工具、服务和组件；新增抽象或依赖应有明确用途，并在 PR 中说明必要性。
  • 处理异常、边界数据与资源清理。修复缺陷或改变行为时，按影响范围补充能验证行为的回归测试。
  • 行为、接口或约定发生变化时同步维护相关文档；不提交密钥、本机配置或与改动无关的生成产物。

知识文档

修改 doc/ 下的内容时，遵循 doc/AGENTS.html 中的知识组织要求，参考现有文档结构与元数据约定。新增、移动或调整分类时同步维护 doc/SUMMARY.html，检查相对链接和图片引用；重要结论给出来源与适用边界。

本地开发与验证

使用根目录 .node-version 指定的 Node.js 26，与 CI 保持一致。Cloudflare Pages 也通过该文件选择 Node.js 版本，避免平台默认版本缺少 jsdom/undici 所需的运行时 API。

Cloudflare Pages 后台已有 NODE_VERSION 环境变量时，应将 Preview 和 Production 的值同步设为 26；仅更新仓库里的 .node-version 不会替换后台已指定的版本。以构建日志中的实际安装版本为准。

通过 npm 安装锁定依赖：

npm ci
npm run dev

Linux 安装会实际调用分词接口检查 nodejieba 原生模块；模块不可用（如预编译包要求更高版本的 GLIBC）时，会自动从源码编译并再次验证。源码编译需要 Python 3、make 和 C++ 编译器。

代码改动提交前运行单元/组件测试和生产构建；涉及页面、交互、路由或构建输出时，再运行 PR 范围的端到端测试：

npm test
npm run build
npx playwright install chromium
npm run test:e2e:pr

端到端测试使用生产构建产物，必须先完成 npm run build；Playwright 会自动启动 preview 服务。test:e2e:pr 排除标记为 @prod、@network 的用例，相关行为有改动时还需按需验证。

E2E 以用户可观察的完整流程为单位，重点保护阅读与导航、搜索到正文、继续阅读、偏好持久化等主流程。同一测试层级避免重复覆盖同一行为；桌面和手机只有输入方式或浏览器行为不同时才分别覆盖。主题切换、弹层打开和关闭等相关操作可放在同一流程中，避免反复启动页面，也避免将无关功能拼成一个长用例。

坐标计算、序列化、指针阈值、取消和异常数据等分支优先在单元/组件层验证。E2E 检查实际操作后的页面、反馈和可用性，避免重复检查内部类名、组件数量或存储格式。曾经失败的跨组件、路由缓存、真实触屏、弹层遮挡等浏览器集成行为保留最小回归；合并用例前确认这些行为仍有明确覆盖。

纯文档改动至少检查内容、Markdown 格式、链接和图片引用；影响站点渲染或目录时补充构建与页面检查。验证命令以 package.json 和 .github/workflows/ 为准。在 PR 中如实记录执行结果，未执行或失败的检查应说明原因。

PR 描述与提交前清单

PR 标题应清楚描述改动。正文说明关联 issue、问题原因、解决方式、影响范围和验证结果；界面改动通过 PR/issue 附件、CI 产物或外部链接提供截图，必要时展示亮暗主题及移动端效果。

图片不得提交到 Git 仓库，包括界面截图、测试截图及生成的可视化图片。本地生成图片应保存在仓库外或已被 .gitignore 排除的输出目录，审阅时使用附件、CI 产物或外部链接展示，不为展示图片而新增仓库文件。

  • 已关联对应 issue，并区分完整解决与部分解决。
  • 改动范围聚焦，符合项目设计、架构和现有代码风格。
  • 已同步相关文档，并按需补充或更新测试。
  • 已完成适用的本地验证，记录结果及未完成项。
  • 已检查 diff，没有混入无关文件、敏感信息或调试代码。
  • 未新增图片文件；所需截图通过附件、CI 产物或外部链接提供。
